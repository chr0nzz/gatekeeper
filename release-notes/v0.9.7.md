# v0.9.7

A stability release. Six fixes to how the server handles slow work, so that one slow operation can no longer stall every other request. Nothing here changes what GateKeeper does, only how well it holds up under load and on small hardware.

---

## Requests can no longer pile up behind a slow database call

GateKeeper serialises every database-touching request through a single SQLite connection. That is the right choice for SQLite writes, but it means the slowest operation in the process sets the delay for every other request, including ones that would otherwise be instant.

Two things made that a stall rather than a slowdown, and both are fixed:

- **No request had a deadline.** Every database call inherited the request's own context, which cancels only when the browser gives up. Behind a proxy that can be a minute or more, so waiting requests accumulated instead of being dropped. Requests now carry a 20 second deadline. Backup upload, download and restore are exempt, since those are legitimately slow.
- **No connection had a timeout.** Both the public and admin listeners ran with every HTTP timeout unset, which means infinite. A connection that opened and then stalled mid-request held a slot forever, and a flaky mobile connection could do that by accident. Header, read, write and idle timeouts are now set on both.

## Automatic backups no longer freeze the server

Taking a backup copies the whole database with `VACUUM INTO`. That ran on the same single connection everything else uses, so for the length of the copy every sign-in, token request and protected-site check was blocked outright. It also got slower as the database grew, so this worsened over time with no configuration change.

The snapshot now runs on its own read-only connection. Backups no longer touch request traffic at all.

## Setting up an authenticator app no longer stalls everything

Enrolling in TOTP generates eight recovery codes and hashes each one. That hashing ran inside the database transaction, so the only connection was held for the entire time.

Measured on a single core machine, that was **1.2 seconds** during which the whole server was frozen. The codes are now hashed before the transaction opens, so it is held only for the inserts.

## Password hashes record their own settings

Stored password hashes contained only the salt and the hash, with the argon2 settings taken from constants in the code. Changing any of those settings, for example to tune for a smaller server, would have made **every existing password fail to verify**, locking out every user and administrator with no recovery other than resetting each account by hand.

Hashes now record the settings used to create them. Existing hashes keep working, and are quietly rewritten in the new format the next time that person signs in. Nothing is required from you and no one needs to reset a password.

## Failed backup uploads no longer stop all future backups

The uploader used an HTTP client with no timeout. If an upload hung, the backup routine never returned, the schedule never ticked again, and backups stopped silently with nothing in the log. The uploader now gives up after ten minutes.

## Upgrading

```bash
docker compose pull
docker compose up -d
```

No configuration changes and no migrations.
