# v0.9.3

Fixes an OIDC regression introduced in v0.9.2 and moves cross-domain ForwardAuth configuration into the admin UI.

**If you are running v0.9.2 with OIDC applications, upgrade.** Sign-in through those apps is broken on that version.

---

## Bug fixes

### OIDC sign-in works again (regression in v0.9.2)

v0.9.2 limited the claims in a `/userinfo` response to the scopes recorded on the access token. Tokens do not always have their scopes recorded, and those tokens then received no claims at all, including no `email`. Applications had nothing to identify the user with, so they returned people to their own login page. From the outside it looked like clicking "Sign in" did nothing.

Claims are now limited only when the granted scopes are actually known. A token without recorded scopes receives the standard claims, which is how v0.9.1 and earlier behaved.

### TOTP recovery codes no longer hang

Redeeming a recovery code wrote to the database while a query cursor was still open. GateKeeper limits itself to a single database connection, so the write waited for a connection that could never be released and the request hung until it timed out. This affected every previous version and was found by the new test suite.

## Protected app domains moved into Settings

A ForwardAuth app on a different domain than GateKeeper needs that domain on an allowlist before users can be returned to it after signing in. In v0.9.2 this required the `REDIRECT_ALLOWED_HOSTS` environment variable and a container restart, and getting it wrong sent users to the GateKeeper home page with no explanation.

- **Set it in the admin UI** under **Settings - Access control - Protected app domains**. Changes apply immediately, with no restart.
- **One consistent entry format.** Each entry covers the domain and all of its subdomains, so `example.net` allows `app.example.net`. Writing `.example.net`, `*.example.net`, or pasting a full URL all mean the same thing.

  Previously a domain written without a leading dot matched only that exact hostname, so `example.net` silently failed to allow `app.example.net`. That distinction is gone.
- The environment variable still works for automated deployments. Entries from both sources are combined.
- Your own GateKeeper domain, your admin domain, and anything under `COOKIE_DOMAIN` remain allowed without an entry.

```
jellyfin.example.net
.example.org
```

## Tests and CI

- **Tests run on every push and pull request.** A GitHub Actions workflow builds, vets, checks formatting, and runs the suite with race detection and coverage reporting.
- **Coverage extended across the application.** Beyond the security behaviour covered in v0.9.2, the suite now exercises password and OTP handling, TOTP enrollment, validation, lockout and recovery codes, backup encryption, configuration validation, database migrations and restore, CSRF, template parsing, and the OIDC claim and redirect rules. Both bugs fixed in this release were found by these tests.
- **Template regression guards.** Three checks catch mistakes that are otherwise invisible until a page breaks in a browser: page-scoped variables used inside a range block, inline scripts missing their CSP nonce, and inline event handlers that a nonce-based policy blocks.

```bash
go test ./...
```

## Upgrading

```bash
docker compose pull
docker compose up -d
```

No migrations or configuration changes are required coming from v0.9.2.

If you protect apps on a domain other than your `COOKIE_DOMAIN` and previously set `REDIRECT_ALLOWED_HOSTS`, you can leave it as it is or move those entries into **Settings - Access control - Protected app domains**.
