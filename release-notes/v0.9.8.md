# v0.9.8

**Upgrade from v0.9.7.** A database setting that was never taking effect caused sign-ins to fail with "database is locked" once backups started running on their own connection. Anyone on v0.9.7 should upgrade.

---

## Sign-ins no longer fail with "database is locked"

GateKeeper passed three settings to SQLite when opening the database: write-ahead logging, a lock wait timeout, and foreign keys. **None of them were being applied.** They were written in the query format of a different SQLite driver, and the driver in use ignores anything it does not recognise, without an error.

That went unnoticed for the life of the project because everything shared a single connection, so nothing could ever contend for a lock. v0.9.7 gave backups their own connection, which was correct in itself but created the first real concurrency the database had seen. Without write-ahead logging a backup blocks writes, and without a lock timeout those writes fail instantly instead of waiting. The result was sign-in attempts failing with `database is locked`, and eventually scheduled backups failing for the same reason. Restarting cleared it until it happened again.

The settings are now written in the format this driver reads, so:

- **Write-ahead logging is on**, which lets reading and writing happen at the same time. A backup no longer blocks anyone signing in.
- **A 10 second lock timeout applies**, so genuine contention waits instead of failing immediately.
- **Foreign keys are on.** No table currently declares one, so nothing changes today, but future ones will be enforced.

## The settings now check themselves

The reason this went unnoticed for so long is that a silently ignored setting looks identical to a working one. GateKeeper now reads back what actually took effect when it opens the database:

- Starting up **fails immediately** if the lock timeout is missing, since that can only mean the settings were not applied.
- A **warning** is logged if write-ahead logging could not be enabled, which is possible on network filesystems, along with the mode actually in use.
- The effective settings are logged on every start: `sqlite ready journal_mode=wal busy_timeout_ms=10000`.

Tests assert each setting takes effect, that writes succeed while a backup is running, and that the connection string contains no parameter this driver ignores.

## A side effect worth mentioning

Write-ahead logging removes a disk sync on every write. The test suite went from roughly eight minutes to one. Expect writes to be noticeably quicker in normal use too.

---

## Upgrading

```bash
docker compose pull
docker compose up -d
```

No configuration changes and no migrations. The database switches to write-ahead logging on first start, which is a one-time change to the file and needs nothing from you. Check the startup log for `sqlite ready journal_mode=wal`.
