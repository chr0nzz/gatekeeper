# v0.9.2 - Security release

An independent security audit of the codebase produced 14 findings. All of them are fixed in this release, and the repository now has a Go test suite covering the changes.

Two changes affect running deployments. See [Upgrade notes](#upgrade-notes) before pulling.

---

## Cross-domain sign-in (critical)

Signing in to an app on a different domain used to work by putting a signed copy of the session identifier into the redirect URL. Anyone who could read that URL - a proxy log, an access log on the destination app, browser history - could take over the session. On top of that, `redirect_uri` was followed wherever it pointed, so a crafted login link could deliver a logged-in user, and their token, to an attacker's site.

The handoff was redesigned rather than patched:

- The token in the URL is now a **random reference** to a server-side record. It contains no session or user data.
- It can be **redeemed once**, enforced by an atomic database update.
- It is **bound to the destination host** and refused anywhere else.
- It **expires after two minutes**.
- On redemption the destination app receives a **brand new session** of its own.

Redirect targets are now checked against an allowlist. Relative paths always pass. Absolute URLs must match your `BASE_URL` host, `ADMIN_URL` host, `COOKIE_DOMAIN`, or the new `REDIRECT_ALLOWED_HOSTS` setting. Everything else falls back to the home page.

The ForwardAuth debug log now records the request path only, so a token can no longer appear in your logs.

## QR sign-in (high)

An approved QR code could be polled repeatedly, and **every poll issued another session**. Approval could also be phished: send someone an approval link, have them tap Approve, then collect the session yourself.

- A code is now **claimed exactly once**, atomically.
- Claiming requires a cookie set on the **browser that displayed the code**, so whoever started the flow is the only one who can finish it.
- The approval form is CSRF protected.

## Admin panel (high)

A display name containing markup was written into the admin command palette without escaping. Any user could set their name to a payload and run script in an admin's browser the next time that admin searched - a direct path from ordinary user to full admin. Values are now escaped where they are inserted.

Supporting fixes:

- **Content-Security-Policy** no longer allows inline script. `script-src` carries a per-response nonce, so injected script is blocked by the browser even if it reaches a page. All inline event handlers were converted to delegated handlers to make this possible.
- **Admin login is rate limited**, and the throttle runs *before* the deliberately expensive password hash. This closes both online password guessing and a way to exhaust server memory with concurrent requests.

## Accounts and data at rest

- **Trusted devices are opt-in.** Passing two-factor authentication no longer silently trusts the browser for 30 days. There is a checkbox, and the token only works in the browser it was issued to.
- **Session and trusted-device tokens are hashed** in the database. A copy of the database no longer yields working credentials.
- **Third-party secrets are encrypted** with AES-256-GCM: SMTP password, S3 keys, social login secrets, webhook tokens.
- **Pre-v0.4.0 TOTP secrets are retired.** Those were stored with a scheme recoverable from a database read alone. Affected users are asked to enroll their authenticator again rather than having the weak secret quietly reused.

## Outbound requests and OIDC

- **Internal addresses are blocked.** Client icon URLs and webhook endpoints could be aimed at loopback, private ranges, or the cloud metadata service - and for icons, the fetched content was then served back publicly. Destinations are now resolved and checked on every connection and redirect.
- **Icons must really be images.** Fetched data is content-sniffed and rejected otherwise.
- **`end_session` validates its redirect** against registered client redirect URIs.
- **Claims respect granted scopes.** `email` and `profile` are only returned when those scopes were granted, and `email_verified` now reflects whether the address was actually confirmed instead of always reporting true.
- **Client secrets are compared in constant time.**

## Tests

The repository now ships a Go test suite covering the security-relevant behaviour: single-use and host-bound handoff tokens, redirect allowlisting, QR single-use and browser binding (including a concurrent-claim race test), token hashing at rest, rate limiting, settings encryption, CSP nonce handling, and the internal-address blocklist.

```bash
go test ./internal/...
```

## Upgrade notes

**1. Everyone signs in again.** Session and trusted-device tokens are now hashed, so tokens issued before this release no longer match. This is a one-time effect of the fix.

**2. Cross-domain ForwardAuth needs configuration.** If a protected app is on a different domain than your `COOKIE_DOMAIN`, list it or sign-in will return users to the GateKeeper home page instead of the app:

```yaml
environment:
  REDIRECT_ALLOWED_HOSTS: ".example.net,.example.org"
```

Entries are an exact hostname (`app.example.net`) or a domain suffix (`.example.net`, which also covers subdomains). Apps under `COOKIE_DOMAIN`, plus your `BASE_URL` and `ADMIN_URL` hosts, are always allowed and need no entry.

**3. Very old TOTP enrollments must re-enroll.** Only affects secrets created before v0.4.0. Those users sign in with an email code and set up their authenticator again.

```bash
docker compose pull
docker compose up -d
```

After upgrading, verify QR sign-in and one ForwardAuth-protected app.
