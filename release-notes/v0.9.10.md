# v0.9.10

**Security release.** Upgrade from any earlier version.

---

## Disabled users lose app access right away

Disabling a user or revoking their sessions now deletes their app tokens. Disabled and deleted users can no longer refresh a token or read their details from the userinfo endpoint. A token also has to be stored and unexpired to be accepted there.

## Token introspection reports revoked tokens as inactive

The introspection endpoint, which services call to check a token, reported expired, revoked and disabled users' tokens as active. It now reports them as inactive. Active responses also include the scope, client and expiry.

## Refresh tokens work once

Using a refresh token now ends the old pair and issues a new one, so a stolen refresh token cannot keep working alongside the real app.

Apps must save the new refresh token each time. An app that reuses an old one has to sign in again.

## Forced password changes apply to forward-auth

A user flagged by an admin who already has a session is now sent to change their password before reaching a protected app, then returned to it.

## The login limit can no longer be avoided with a fake header

GateKeeper trusted the `X-Real-IP` header from its proxy. When Traefik is set to trust the service in front of it (`forwardedHeaders.trustedIPs`), a header sent by the client passes through unchanged, so a client could fake it to avoid the login attempt limit.

GateKeeper now ignores `X-Real-IP` and takes the client address from `X-Forwarded-For`. A proxy in front of GateKeeper must send that header. Traefik does by default, and the nginx examples in the docs already do.

## Dependencies

Updated chi to v5.5.0 to clear advisory GHSA-j6qf-3m9c-vwj3. GateKeeper does not use the affected function.
