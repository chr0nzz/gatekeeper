# v0.9.6

**This is a critical security release. Upgrade immediately and read the rotation notes below.**

---

## Critical: the JWKS endpoint published the private signing key

The public key endpoint at `/keys`, which OIDC applications use to verify token signatures, served the full RSA private key instead of only the public half. The response included the private exponent and prime factors (`d`, `p`, `q`, `dp`, `dq`, `qi`), which is the complete key. The endpoint is unauthenticated by design, so anyone who fetched it could sign tokens that every application trusting your GateKeeper accepts, with any identity and any claims.

The cause was a one-line mix-up: the structure holding the signing key was reused for the published key set, so the private key was serialised where the public key belonged. It now publishes only `kty`, `n`, `e`, `kid`, `alg` and `use`, a test asserts that none of the private fields can ever appear in the response, and the type system now separates the signing key from the published set.

**What is and is not affected.** The key signs OIDC id_tokens only. Sessions, access tokens, refresh tokens, handoff tokens and ForwardAuth cookies are opaque random values checked against the database and cannot be forged with this key. The risk is anyone validating JWTs against your `/keys`: OIDC applications and any middleware doing local token verification.

**Rotation is automatic and mandatory.** Upgrading deletes every stored signing key, since all of them have been published, and generates a fresh one on startup. You do not need to do anything for that part. You should additionally:

1. Check your reverse proxy access logs for requests to `/keys` on your auth domain to see who fetched it.
2. Restart or re-login any OIDC application that caches the key set for a long time, so it picks up the new key.
3. If any application does local JWT validation with a pinned or long-cached key set, clear that cache now. Until it refreshes, it will still accept tokens signed with the leaked key.

Signing in again at each application is enough for normal setups. Nothing needs reconfiguring.

## Honest sign-in labels

Every sign-in in the audit log was labelled **Password** unless it used a passkey or a social provider. The completion step wrote one generic event no matter how the user authenticated, and the label was derived from that event alone. Opening an application while already signed in wrote the same event, so signing into a website through OIDC appeared as a password login even though nothing was typed.

The method now travels with the sign-in and the label follows it:

| Sign-in | Was labelled | Now labelled |
|---|---|---|
| App opened with an existing session | Password | SSO |
| Passwordless email code | Password | Email OTP |
| Trusted device | Password, twice | Trusted device, once |
| Social provider via OIDC | Social and Password, two rows | Social, one row |
| QR code | no label | QR code |
| Password (with or without a second factor) | Password | Password |

The duplicate rows also inflated the dashboard's sign-in counts, so those become accurate too. The audit page has filter chips for the new labels. Entries written by earlier versions keep their old labels.

## The audit log shows what was signed into

A new **App / Site** column answers the other half of the question. Sign-ins through OIDC show the client's name, such as Immich. Sign-ins that came from a ForwardAuth redirect show the site's hostname, such as `radarr.example.com`.

Two new events cover what was invisible before:

- **`login.handoff`** - written when an existing sign-in reaches a protected site on another domain, once per site rather than once per request, so the log stays readable.
- **`forwardauth.denied`** - written when a signed-in user is refused by a site's access policy, with the site and the policy name. Denied access attempts were previously not recorded anywhere.

To make room, the User and Email columns are merged, with the email shown on hover, and the Method badge is folded into the event, also shown on hover. The method filter chips still work. Audit rows for admins now show their display name instead of their email, as user rows always did.

## The wrong email on a duplicate registration

Trying to register with an address that already has an account sent that address a message headed "Password changed", telling the recipient their password had just been changed and to contact their administrator immediately. Nothing had changed. The subject was right, the body was the password-changed template. It now says an account already exists and that no action is needed.
